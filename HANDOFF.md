## Проход 5 — комплект для проверки одной живой записи в среде владельца

Проход 4 принят проверяющим (adcb62f, 198 тестов). Проход 5 не касается

сам провести проверку записи в своей среде».

1. **`examples/proxy_check.py`** — doctor / run (dry-run | live) / replay /
   review-package:
   - `doctor` — ffmpeg/ffprobe, свободное место против бюджета, валидность
     настроек прокси (без трейсбеков), доступность /proc; пишет doctor.json;

     подтверждением (`SECRETARY_LIVE_CONFIRM=1` + `--live-yes`), иначе
     блокируется ДО создания заданий (exit 2);

     обязательны (exit 1, список имён) — выбор до распаковки (новый
     `scan_entries` в zipimport без извлечения + `audio_filter` в
     `import_zip`, все защиты ZIP сохранены);
   - `replay` — возобновление строго по job_id из check-run.json
     (область pass3 не нарушается; чужие задания не трогаются — тест);

## Проход 4 — замечания проверяющего агента к eb359c9

P1 «ложноположительный итог запуска» закрыт кодом, юнит- и E2E-тестами
и демо шести прогонов (контроль + 4 сценария ревью):

1. **Итог учитывает ВСЕ аудио-задания текущего импорта** — новая
   `compute_transcription_status(job_ids, statuses)`: счётчики
   `{expected, completed, partial, failed, cancelled, not_finished,
   missing}` по каждому job_id из манифеста текущего запуска (run scope
   прохода 3 сохранён); любой не-`completed`, отсутствующий или
   оставшийся в очереди статус понижает этап как минимум до `partial`,
   без единого успешного результата — `failed`.
2. **Пустой attempted=0 — не complete** — `compute_publication_status`
   получил параметр `expected` (документы + completed-расшифровки) и
   значение `nothing_to_publish`: при непустом ожидании пустой счётчик —
   `failed`, при пустом ожидании — отдельный честный статус вместо
   «complete» (раньше давало exit 0 — воспроизведено до фикса по
   методике ревью).
3. **Три независимых статуса в отчёте** (этапы не смешиваются):
   `transcription_status` (расшифровка), `publication_status`
   (публикация), `workflow_status` (итог, задаёт код возврата 0/1/2/3) +
   счётчики обоих этапов и человекочитаемый `reason` при `failed`.
   Пример: «документ OK + аудио упало» → transcription failed /
   publication complete / workflow partial / exit 2.
4. **Коды возврата соответствуют итогу**: `workflow_status=complete`
   (все аудио completed И все ожидавшиеся загрузки прошли) → 0;
   `not_confirmed` → 1; `partial` → 2; `failed` (ни одного
   опубликованного материала, включая «нечего публиковать») → 3.
5. **Четыре регрессионных сценария ревью** (тесты + демо):
   только упавшее аудио → exit 3; успешный документ + упавшее аудио →
   exit 2; отсутствующий job_id (фазы, симуляция потери строки SQLite) и
   задание, оставшееся в очереди (полный запуск: бюджет диска больше
   свободного места — реальный путь run_job → requeue) → exit 3; архив,
   где все элементы отклонены → exit 3. Плюс контрольный прогон «всё
   успешно» → exit 0.
6. **Исправления проходов 2–3 не тронуты**: run scope, батчинг ≤5,
   /api/healthz, отсутствие verify_admin, обязательное подтверждение
   человеком (phase_review без изменений, все старые тесты зелёные).
   Для офлайн-демо упавшего прокси добавлен
   `SECRETARY_FAKE_TRANSPORT_FAIL=1` (работает ТОЛЬКО с
   `--fake-transport`, живой режим не затронут).

   `ok > 0`, а не «всегда true»; в отчёте

   счётчики `publication: {attempted, ok, failed}` и per-item результаты;
   отказы (HTTP/сеть/расширение) фиксируются поштучно и не прерывают

5. **Батчинг загрузок (P2)**: upload режется на запросы не больше

   `continue_on_error=True` у оркестратора: отказавший батч не прерывает
   остальные. Тело запроса в RAM — только одного батча.
6. **verify_admin удалён (P2)**: локальная «проверка» по фиктивному
   `server-token-unknown` не могла подтвердить настоящего администратора

   источником истины (тест фиксирует отсутствие метода).

### Этап 1 — надёжная расшифровка
- Python 3.12+ / stdlib only (внешних pip-зависимостей нет); ffmpeg/ffprobe
  списком аргументов, без shell; таймауты; rlimits на Linux; проверка
  свободного места (disk budget).
- Локальные MP3/M4A/OGG/WAV: allowlist расширений + сигнатуры контейнера +
  ffprobe-подтверждение (действительный формат, длительность, аудиопоток);
  размер/длительность с лимитами; отдельная папка на job; SHA256 исходника.
- Сегментация с перекрытием; границы/статусы/результаты сегментов в SQLite;
  дедупликация фраз на стыке перекрытия (по нормализованным строкам);
  границы `[SEG n]` — измеренные границы нарезки, отметки модели отдельно
  помечаются предупреждением и не выдаются за измеренные.
- Транспорт прокси отдельным классом; URL/ключ/модель из конфигурации;
  таймаут; bounded retry (backoff + полный джиттер, Retry-After с капом);
  отмена между попытками; постоянные ошибки не повторяются; HTTP 200 с
  ошибкой/пустым ответом — не успех; сегмент больше лимита автоматически
  делится.
- Перезапуск продолжает незавершённые сегменты; partial/failed ≠ completed;
  версии профиля/модели/промптов в provenance и в params_hash; идемпотентность
  (владелец + SHA256 + параметры); изоляция владельцев.
- Полный транскрипт дословно; `[неразборчиво]` без выдумывания; нейтральные
  метки говорящих; структурирование отдельным шагом (summary, темы,
  утверждения, сомнительные места со ссылками на сегменты), при сбое
  структурирования транскрипт сохраняется.

  таймаут, санитизация ключа в ошибках и repr;
- аудио (реальные ffmpeg/ffprobe 7.1.5 на синтетическом синусе): probe
  длительности, план сегментации (покрытие/перекрытие/слияние хвоста),
  извлечение сегмента Opus, мусор отклоняется;
- движок (фейковый транспорт/аудио): completed/partial/failed, повторы,
  исчерпание + retry-failed, отмена и возобновление, сплит oversized,
  идемпотентность, изоляция двух задач, восстановление после «краха»,
  отсутствие секрета в логах, структурирование с чанками и слиянием,
  сбой структурирования сохраняет транскрипт;
- приёмочный сценарий: синтетический архив ТОЧНОГО состава Хорш.zip
  (PDF + PPTX + DOCX + 4 MP3 + 1 M4A) — реальный ffmpeg конвейер +
  fake прокси, все 5 заданий completed, PPTX принят, результат валиден
  против JSON Schema, конвертированные сегменты удалены;
- HTTP API E2E: полный цикл create→progress→result/markdown, 409 в
  процессе, 400/404/401, дубликат 200, отмена, retry-failed; потоковая
  загрузка (многокусоточное тело), отказ сверх лимита, отказ chunked,
  non-loopback без токена, санитизация 500;
- авторизация tma: подпись/свежесть/allowlist/кодирование заголовка —
   против мока с настоящей проверкой (подпись HMAC, 401/403, контракт
   ответа 200/201, category-валидация), смоук оркестратора;
- отказоустойчивость создания задания: сбой копии, крах между БД и
  rename (ленивое восстановление), move_source, дубликаты;
- область действия запуска (pass3): run_pending(job_ids) не трогает
  чужие queued/completed, E2E-регрессия «A в БД, импорт B, архив C —
  публикация строго своих job_id», уникальные владельцы запусков;
- статусы публикации (pass3): complete/partial/failed/not_confirmed,
  счётчики, поштучные отказы, коды возврата 0/1/2/3, «published не
  true при ошибке»;
- итог запуска по всем заданиям импорта (pass4):
  transcription/publication/workflow-статусы, пустой attempted=0 —
  не complete, четыре сценария ревью E2E (упавшее аудио; документ +
  упавшее аудио; отсутствующий/оставшийся в очереди job_id; полностью
  отклонённый архив) + контрольный exit 0;
- батчинг клиента (pass3): 12 файлов → 3 запроса по 5, лимит байт,
  «сверхбольшой» отдельно, continue_on_error собирает отказы,
  healthz строго по /api/healthz, verify_admin отсутствует;
- CLI smoke: selftest, transcribe --fake-transport --markdown на
  настоящем WAV (маркеры границ, provenance, чистые предупреждения).

Категории доказательств раздельно:
- **моки/детерминированные**: всё выше с FakeTransport/loopback-моком;
- **реальный ffmpeg/ffprobe**: тесты аудио и приёмочный архив;
- **живые внешние API**: НЕ использовались (см. ниже).

## НЕ проверено (честный список)

1. **Живой прокси** (`antigravity-claude-proxy`): ни одного реального
   запроса; имя модели, способ авторизации (`x-api-key` vs Bearer) и
   поведение `type: audio`/`image`-обёртки требуют одной короткой
   реальной записи по договорённости с владельцем.
2. **Реальный приёмочный архив владельца Хорш.zip** — состав
   воспроизведён синтетически БЕЗ подмены набора (PDF+PPTX+DOCX +
   4 MP3 + 1 M4A, включая «длинную» M4A на несколько сегментов);
   сам оригинальный архив не прогонялся (у агента его нет).
3. **Качество расшифровки** реальной речи: не измерялось; никаких
   заявлений о точности нет и не делается.
4. **Ресурсы на целевой VM ~1 ГБ**: замеры RSS/диска не проводились;
   запуск на малой VM согласовать отдельно (AGENT_TASK.md).
5. **Длительные записи** (часы): сегментация и возобновление покрыты
   тестами на коротких файлах; многочасовой прогон не выполнялся.
6. **Публикация в реальный AgroBot**: адаптер/клиент/оркестратор
   демонстрируются на моке, который проверяет авторизацию так же, как
   настоящий tmaAuth (подпись HMAC, свежесть, allowlist); живой
   staging-прогон с настоящим initData и настоящей загрузкой документа
   не выполнялся.
7. **Google Drive-ссылки**: осознанно отложены (SSRF/редиректы/права/
   лимиты) — следующий этап по AGENT_TASK.md.
